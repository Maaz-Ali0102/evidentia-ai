## Key findings

1. **Severe imbalance.** benign 989,534 (94.62%), suspicious 52,564 (5.03%),
   malicious 3,720 (0.36%).
2. **Only two organisations carry the minority classes:** ORG-0004, ORG-0005 have ≥500 malicious training rows.
3. **Alerts come from two log types.** 99.77% of suspicious+malicious training rows are `firewall_action` or `network_flow_data`
   (out of 470 message types).
4. **Malicious events are bursty.** 54.41% of malicious training rows fall in one hour of the day (11:00 UTC).
5. **Heavy duplication.** 59.03% of malicious rows repeat an exact text; malicious rows form only
   37 digit-masked templates; 40.70% of malicious rows share their exact text with rows of another label.
6. **Missingness is class-dependent** (largest gaps: `protocol` 99.75%, `dst_ip` 97.95%, `dst_port` 97.20%, `src_port` 91.82%).
7. **Post-label columns leak the label** (all-benign baseline macro-F1 0.325):
   `lifecycle_stage` — one-feature macro-F1 0.998; `attack_techniques` — one-feature macro-F1 1.000; `attack_tactics` — one-feature macro-F1 1.000; `set_roles` — one-feature macro-F1 0.890; `label_confidence` — one-feature macro-F1 0.898; `matched_rules` — populated only for alert rows (suspicious F1 0.988); `mo_name` — populated only for malicious rows (malicious F1 1.000); `status_name` — populated only for malicious rows (malicious F1 1.000); `suspicion_score` — populated only for malicious rows (malicious F1 0.987); `incident_ids` — populated only for malicious rows (malicious F1 0.164); `disposition` — post-incident engine status (NMI 0.118, macro-F1 0.604); `defense_techniques` — no information in this capture (constant/empty); removed because it is a post-incident field; `disposition_category` — no information in this capture (constant/empty); removed because it is a post-incident field; `is_false_positive` — no information in this capture (constant/empty); removed because it is a post-incident field.
8. **Kept event fields also encode the log type.** Best source field `product_name` scores 0.662 alone,
   but kept field `dst_port` scores 0.733 because it is populated in 1.45% of benign vs
   97.78% of suspicious rows.

## Five modelling decisions justified by the EDA

1. **Class weighting + imbalance-aware metrics.** Because malicious is 0.36% of rows, models use
   `class_weight="balanced"` and are judged by macro-F1, per-class recall and PR-AUC — not accuracy (all-benign would score 94.62%).
2. **Drop post-label columns** (`lifecycle_stage`, `attack_techniques`, `attack_tactics`, `set_roles`, `label_confidence`, `matched_rules`, `mo_name`, `status_name`, `suspicion_score`, `incident_ids`, `disposition`, `defense_techniques`, `disposition_category`, `is_false_positive`): each is produced by the labelling/correlation step;
   the per-column evidence is in finding 7 and chart 9.
3. **Exclude source/collection fields from main models** (`product_name`, `stream_name`, `vendor_name`, `pipeline`) and identifiers (`org_id`, `origin`,
   `timestamp_source`, `artifact_id`); source fields are only added back in an ablation. Because kept fields also reveal the log type
   (finding 8), benign-vs-alert scores are reported as log-type recognition, not threat detection.
4. **Temporal, incident-aware splits per organisation, plus cross-organisation tests** — never random. Bursty malicious
   activity (finding 4) and template duplication (finding 5) would make a random split leak near-identical rows into test.
5. **Hierarchical task + context features.** Benign-vs-alert is mostly log-type recognition (finding 3), and text cannot fully separate
   suspicious from malicious (finding 5), so stage 2 (suspicious vs malicious) adds past-only behavioural context features and is
   evaluated on a "novel text" subset as well.

## Known limitations

- Labels come from WitFoo Precinct's automated correlation, not analyst-verified ground truth (dataset card).
- Coverage is uneven (span per org, all rows): ORG-0001 0.8 days, ORG-0003 0.8 days, ORG-0004 5.8 days, ORG-0005 0.8 days.
- Only ORG-0004, ORG-0005 have ≥500 malicious training rows; their malicious rows come from these log streams
  (ORG-0003: microsoft-windows-security-auditing; ORG-0004: aws_vpc_flow_log, Crowdstrike Detection; ORG-0005: cisco_asa, barracuda_waf), so cross-organisation transfer is structurally hard.
- `mo_name` of malicious training rows: {'Data Theft': 3720} — a single modus operandi, so attack-type classification is not possible.
- `timestamp` is ingest time (dataset card); device `event_time` is not loaded here — see `reports/DATASET_AUDIT.md` §8 (full data) for its coverage.
- The leakage scoring window holds 347 malicious rows, by org {'ORG-0005': 327, 'ORG-0004': 19, 'ORG-0003': 1}; malicious scores mostly reflect one organisation.
- 137 malicious training-side rows belong to incidents that cross a cut-off ({'ORG-0005': 136, 'ORG-0003': 1}); the training pipeline drops them, these EDA statistics still include them.
